# Taste
- Prefers the primary/default option to be visible directly instead of being hidden behind an accordion or dropdown — e.g. QRIS in the checkout payment picker must show immediately as a selectable radio card above other payment groups, with only a small "Paling cepat"/"Fastest" badge inline, no group header/chip/chevron. Confidence: 0.7
- Prefers exclusive-open accordions: at most one group open at a time — opening another group must close the previously open one, and clicking the same group again closes all (rather than allowing several panels open simultaneously). Confidence: 0.55
- Prefers that closing the UI container holding a selection explicitly CLEARS that selection rather than retaining it hidden — no collapsed-header "Dipilih"/selected summary or duplicate selected logo, no hidden stale submitted value, no silent auto-switch to another option on deselect; submit must require a fresh valid selection. Confidence: 0.55
- Prefers compact single-column row lists over multi-column/card grids for data-dense pricing displays (bulk price tiers): quantity range on the left, unit price on the right, one row per tier — and dislikes narrow columns that split long currency amounts (e.g. "Rp12.500.000" wrapping). Confidence: 0.6
- Dislikes weakening tests to force green: never relax/increase timeouts, loosen assertions, or edit failing tests to make a run pass — instead label flaky/timing failures honestly and let the owner rerun. The one sanctioned exception: a correct test that is normally fast but exceeded vitest's default 5s on a slow CI runner gets an explicit per-test timeout passed inline (third argument to `it(...)`, e.g. `20_000`) matching the pattern other workerd tests in the repo already use (grep for it first) — with assertions and global config untouched. Confidence: 0.55
- Prefers stale status claims in living docs (README/ARCHITECTURE/PRD/agent-rules) be marked superseded with fresh evidence of what is actually deployed, while the CHANGELOG is strictly append-only — new entry at the top, existing entries never edited, rewritten, or annotated with notes (an inline "[DIGANTI …]" annotation added to an older entry had to be reverted by the lead); superseding a past decision is recorded in the new entry/DESIGN.md, not by touching history, and a doc edit that silently drops pre-existing committed entries must be restored byte-for-byte from HEAD (proven by `git diff --numstat` showing 0 deletions and an exact-suffix assert); and prefers focused local verification evidence reported separately from full-suite/integration evidence rather than merged into one blanket claim. Confidence: 0.75
- Prefers minimal, reviewable diffs: keep edits scoped to the changed logic plus its tests/docs, and do NOT reformat files or run whole-file rewrites (especially in files other contributors are editing concurrently). Confidence: 0.5
- When handed an already-precise fix list, expects implementation to start from it directly: no broad re-audit of the surrounding codebase, no new abstraction layer/framework/config, just minimum native fixes at the named spots plus small focused regression tests. Confidence: 0.5
- Prefers no big refactors in passing: orphaned/unused components are not deleted but marked with a short header comment stating they are unused and naming the live component instead. Confidence: 0.45
- Expects UI sizing to stay proportional to its neighbours rather than uniformly enlarged: anything that grew without justification gets shrunk back to its previous proportion, an oversized control is restored to the size of the element it sits beside (e.g. stepper matching the CTA height), and explicitly-called-out exceptions ("steppers stay 44px because they align with the h-11 CTA") must be left untouched. Confidence: 0.5
- When multiple agents work in parallel on one codebase, prefers changes to shared files be strictly additive: never change an existing export's signature (add a new export instead), never edit files owned by the other agent, and in shared docs add a separate paragraph/section so blocks stay separable for staging. Confidence: 0.6
- In a shared checkout where another agent has uncommitted edits, expects verification and VCS interaction narrowed accordingly: no index/worktree-mutating git commands (pull/rebase/stash/checkout/reset/restore), no broad `--fix` formatting/linting, no full test suite or full-repo typecheck — only the named focused test(s) plus a path-scoped `git diff --check -- <own files>` — with an explicit stop-and-report if index-touching commands were already run. Confidence: 0.6
- When a merge brings in another task's committed work, expects conflicts in shared docs resolved ADDITIVELY (both sides' sections preserved, no wholesale ours/theirs), staging only the conflicted files, and never stash pop/drop/reset or discarding autostashed work. Confidence: 0.5
- Prefers reusing existing shared machinery over writing a parallel/duplicate implementation for the new area, and expects every shared-file edit to be listed explicitly in the final report. Confidence: 0.6
- Never hardcode values that already exist as shared constants/helpers (surcharge bps, fee minimums, price floors): always reference the constants so upstream changes propagate automatically. Confidence: 0.7
- Prefers deleting obsolete constants/config outright (after grepping all uses) over keeping them as vestigial placeholders at a "smallest sane" value, when no other invariant depends on them. Confidence: 0.45
- Prefers the agent leave version control, dependencies and deployed environments untouched: no commit, no push, no new dependencies, no touching production/env or remote D1 — commits are the lead's job after review, and dirty worktrees (including unrelated files such as `.commandcode/`) should be left as-is and just reported. Confidence: 0.55
- Expects final reports to state files changed plus actual measured numbers (test files/tests passed, failure names, tsc/lint exit codes) instead of qualitative "all green" claims, and to mark verification still in progress as PENDING rather than claiming a pass/finished state. Confidence: 0.5
- A failing test may only be called "pre-existing" with proof: run the exact same file at the clean base / main checkout first and paste the counts, then compare like-for-like (same file set, same test counts) — repeated unsupported "pre-existing failure" claims are treated as a defect to eliminate, since any delta between base and the branch is a candidate regression that must be attributed explicitly. Confidence: 0.6
- For a single still-uncommitted feature, prefers its accumulated packet/fix-log prose in docs be consolidated into ONE coherent description of the current implementation — redundant or now-wrong new blocks rewritten/removed in place instead of appending corrections on top (intermediate stages kept only if explicitly labelled historical), while genuinely pre-existing dated history is left intact. Confidence: 0.5
- Prefers accessibility tap targets stay ≥44px even when an icon/close button's visual size shrinks (32px visual + invisible pseudo-element hit area), and when a test asserts the old size it expects the assertion converted to the new equivalent (e.g. assert the hit-area class) rather than deleted. Confidence: 0.5
- Expects responsive breakpoint/threshold values to be grounded in measured browser evidence rather than derived or guessed: a threshold chosen without measurement gets corrected to the width where the layout actually fits (e.g. brand name hidden below 375px because at 360px the cart button measured right=361 > 360), and DESIGN.md/CHANGELOG must cite the measurement basis (widths tested, what clipped, what fit, who measured) alongside the class. Confidence: 0.5
- For small-screen layout overflow, prefers the fix scoped strictly to the failing range via arbitrary breakpoint modifiers (`max-[374px]:…`) plus nowrap/truncate/shrink-0 so every width above the threshold renders pixel-identical to before — compacting by hiding decorative icons/optional hints while NEVER hiding loading feedback (e.g. the pending checkout spinner stays visible). Confidence: 0.5
- Prefers verification/QA batched at the end ("QA diakhir", no repeated QA per change): don't loop on tests, typecheck, browser checks, or reviews after each edit — report completion concisely and honestly (including deferred verification) instead. Confidence: 0.6
- Prefers adjacent/out-of-scope problems be reported with file:line evidence rather than fixed when the fix would change state machines or server semantics: only small, low-risk fixes are made in passing; anything riskier is documented and left for an explicit owner decision. Confidence: 0.5
- Exception to the above: when a flagged "judgement call / risk note" is actually a real correctness bug (e.g. writing stock to the wrong table on cancel), the owner expects it fixed NOW, minimally, keeping the existing status transitions/guards — and fixed defensively at the shared choke point (a guard in the shared helper/transition so every current and future caller is safe) in addition to the named call sites, not just patched where the agent happened to notice it. Confidence: 0.55
- Expects parallel surfaces (e.g. Market web checkout and the Pedia order client) to behave identically when the same server error contract applies — a documented "known limitation" on one surface while the other already recovers properly is treated as a bug to fix, not to report. Confidence: 0.55
- Expects claims about which surfaces/features a change affects to be verified at the actual call site (file:line) before they go into docs or the final report; inferring "shared function ⇒ other surface affected" is treated as a wrong claim to correct. Confidence: 0.5
- On checkout/payment state machines, expects hard invariants preserved rather than re-derived: never two live invoices for one checkout, never double-reserve or double-restock stock (restore exactly once), and idempotent behavior under repeated taps and concurrent callbacks using the existing nonce/claim guards. Confidence: 0.5
- Expects operational/setup guidance in docs (README/ARCHITECTURE) to be actually executable against the deployed architecture: a procedure that cannot work in production (e.g. suggesting Bot API `getUpdates` for a group ID while the bot uses an active webhook) must be corrected to an accurate, non-secret method, and the fix must never be "disable the webhook" or add new production operations. Confidence: 0.5
- On payment/claim flows, prefers fail-closed semantics: an irreversible state change (cancelling an order, marking a claim terminal) is allowed ONLY when the failure is proven definitive by a read-only confirmation, while every ambiguous case (timeout, network, unreadable/5xx proxy response, rate-limited or non-404 confirmation read) keeps today's behavior and the claim intact — and the provider is never re-POSTed. Confidence: 0.6
- Test/verification commands must be run with `env -u NODE_ENV` (the shell exports `NODE_ENV=production`, which makes routes 503/misbehave under vitest) — this escaping convention is the accepted baseline for all focused runs. Confidence: 0.55
- Prefers multi-write invariants be made atomic with the platform's native primitive (e.g. a single `D1.batch` covering snapshot + enqueue-all + freshness marker) so any failing statement rolls back all of them — never "write the new value then try to roll back", and when native atomicity is unavailable the operation must fail closed (keep last-good) instead of proceeding. Confidence: 0.6
- Expects no silent truncation or partial success in data pipelines: oversize text is flagged unavailable rather than sliced, a batch is never sliced-then-acked (unprocessed work stays in a durable, recoverable queue), and freshness/success markers are written only after the whole validated snapshot persists — partial writes are reported as failures, never as 200/ok. Confidence: 0.6
- Expects machine/sync-generated data never to overwrite human-controlled state: ownership is checked before any mutation (colliding curated slugs stay untouched), admin overrides (price group, markup, min-profit) survive repeated syncs, and human disables/manual locks dominate machine status changes. Confidence: 0.55
- When shared-file ownership is reassigned mid-task in a same-tree multi-agent run, expects an immediate short acknowledgment that writes to those files stopped, existing edits there preserved rather than reverted (left for the new owner to integrate), and the now-deferred updates recorded in external notes — while continuing only in the files still owned and never overwriting or staging another task's in-flight changes. Confidence: 0.5
