# MAP-4 — Feature-readiness map: reseller / affiliate / members / reseller API / new supplier types

Read-only architect map. Base main @ad711d6f. All claims file:line. Nothing built; this says what must exist first.

## 1) Order creation — entry points, shared vs duplicated

Every `INSERT INTO orders` in `src/`:

| Entry point | Insert site | Paid-path logic |
|---|---|---|
| Web checkout | `src/app/api/orders/route.ts:514` → `createOrderWithStock` (`src/lib/db/orders-create.ts:32,262`) | Route does: rate limit (:173), zod, signed-quote verify (`verifyCheckoutQuoteToken` auth.ts:648; quote issued by `src/app/api/checkout/quote/route.ts` via `createCheckoutQuoteToken` auth.ts:626), slug canonicalisation, item-set equality vs quote (:216-222), buyer-field equality (:223-229), email-required guard (:239-276), min/max-qty re-check (:285-343), price-staleness re-check (:348-385), payment-method-in-token check (:392-400), crypto/gateway re-derivation (:405-481), anti-abuse `consumeCheckoutSlot` (`src/lib/checkout-guard.ts`, HMAC subjects ip/wa/email, 5/3/3 per 15 min), then atomic stock+order batch; QRIS/crypto/gateway invoice issuance **after** insert (:548-612) with cancel-on-setup-failure via `transitionPendingOrder` |
| Telegram | `src/lib/telegram/handlers/{invoice.ts:297,payment-dispatch.ts:175,cart-invoice.ts:115}` → `createChannelOrderAtomic` (`src/lib/commerce.ts:108`) | commerce.ts is the channel-shared module (header :2-4): builds items/lines itself, calls the other atomic writer `reserveChannelOrder` (commerce.ts:189,487 INSERTs), idempotent via `operation_guards`/quote_id, `isExisting` dedupe |
| Games | `src/app/api/games/orders/route.ts:202` | Own route-level batch INSERT (order_kind='games'), own quote_id claim (`owned` EXISTS guard :197), payment via shared `payment_transactions` rails afterwards |
| Pedia (SMM) | `src/app/api/pedia/orders/route.ts:251,256` | Own route INSERT with `payment_status='paid',paid_at` at creation + `pedia_order_items` snapshot rows; balance/credit logic is Pedia-specific |
| TUNVN/AIVault/StoreBat/Mirai/WR/SK | no INSERT — they are fulfillment suppliers | Links are created post-payment from the paid order: `createXxxOrderLinks(orderCode)` (e.g. tunvn/orders.ts:59, aivault/orders.ts:27) invoked by `src/lib/payments/paid-fulfillment.ts` + cron |

**Verdict: two-and-a-half order-creation paths, not one.** Web (route + orders-create.ts) and Telegram (commerce.ts) share *helpers* (`buyer-fields.ts` eligibility/snapshot checks are imported by both: orders-create.ts:11, commerce.ts:22; `bulk-pricing.ts`; `order-access.ts`) but each re-implements validation ordering, price binding and the atomic batch separately (orders-create.ts:42-77 supplier-eligibility SQL vs commerce.ts's own line building). Games and Pedia bypass both entirely. There is **no** callable "place order" domain function: web's logic lives inside a 906-line route handler coupled to `NextRequest`, quote tokens and payment-rail branching.

**What a reseller API needs / extract first:** a channel-agnostic `placeOrder(actor, lines, paymentInstruction) → {orderCode, payable}` extracted from the web route's sequence (validate → price-bind → anti-abuse → atomic reserve → issue payment), with sales channel as data. Blocker: `orders.sales_channel` CHECK is `('web','telegram','whatsapp')` (schema.sql:83-84) — an `'api'` channel needs a schema change (SQLite CHECK = table rebuild migration) plus every `sales_channel` switch in fulfillment/notify. Also `orders.customer_wa TEXT NOT NULL` (schema.sql:70) forces a contact shape API buyers may not have.

## 2) Pricing — can a reseller price tier be added in one place today? No.

- Sell price is **materialised into `product_variants.price` at sync time**, per supplier, each with its own formula: WR `calculateSellPrice` (warung-rebahan/sync.ts:184-187, applied :543), SK `calculateSkSellPrice` (sekalipay/sync.ts:328-329), plus per-supplier markup modules `src/lib/{aivault,storebat,mirai,tunvn}/markup.ts` (mirai also `pricing.ts`). Bulk qty tiers exist but are quantity-only (`resolveBulkPriceForProduct`, bulk-pricing.ts:65).
- Read paths read `variants.price` directly: catalog, quote route (`src/app/api/checkout/quote/route.ts:203-222,353`), Telegram keyboards.
- Re-validation happens **three times**: quote issuance, orders route (:362-381 compares quote price vs live `resolveBulkPriceForProduct`), and inside the atomic reservation (orders-create.ts:42-45 re-reads `pv.price`).

There is no customer dimension anywhere in pricing — price is a property of the variant, identical for all buyers. **Minimal extraction:** one `resolveSellPrice({variantId, qty, priceTier}) → {unitPrice, tierApplied}` used by quote issuance, catalog display and the API; tier defaults to retail so web/TG are unchanged. The markup-at-sync materialisation can stay (it produces the *retail* base), but reseller price cannot be a sync-time column per tier without exploding sync — it must be computed at quote time from cost/base. Owner decision needed: reseller price = % off retail, or cost+own-markup (needs cost exposure rules — cost today is admin-only, cf. supplier-wr-sk.md modal rules).

## 3) Identity — buyers today, admin auth, what transfers

**Buyers have no account.** Identity = order code + capability proof: `customer_wa`/`customer_email` columns on orders (schema.sql:69-71), PIN6 access (`buyer_access_format IN ('code26','pin6')` :76), proof objects c1/p1 and 30-day device cookie d1 (docs/agent-rules/buyer-credentials.md; `src/lib/order-access.ts`, `src/lib/order-device-cookie.ts`, PIN attempts `src/lib/orders/pin-attempts.ts`). Telegram buyers: `telegram_users` (schema.sql:301, PK = TG user_id, saved email/locale). There is **no members/users table** (97 tables; only `telegram_users`, `orders`, `agent_tokens`).

**Admin auth is single-person by construction:** one `ADMIN_EMAIL` + password hash + JWT (`src/lib/auth.ts:107-117,355,723`), fronted by Cloudflare Access whose check is literally `payload.email === ADMIN_EMAIL` (`src/lib/cloudflare-access.ts:38-41`).

- **Must NOT be reused for members/resellers:** admin JWT/`requireAdmin` (all-or-nothing), the Access app (single-email), `ADMIN_JWT_SECRET` as a general session secret, buyer PIN/proof (order-scoped capability, not identity — anyone with code+PIN *is* the buyer for that order).
- **Can be reused:** `checkRateLimit` (`src/lib/rateLimit.ts:122`), bounded body reads (`src/lib/http-body.ts:13`), `checkout-guard.ts` HMAC-subject admission pattern, audit style of `agent_tokens`/`article_audit_log`.
- **Existing reusable precedent:** `src/lib/agent-auth.ts` — scoped bearer API keys done right (SHA-256 hash stored, `axv_` prefix, scopes, expiry, last_used, `requireAgent(req, scope)` :15-25) but bound to article scopes on `agent_tokens`. A reseller key system should clone this shape into its own table, not extend `agent_tokens` semantics.
- **Collision risks:** `orders.customer_wa NOT NULL`; `sales_channel` CHECK (above); `telegram_users.user_id` PK if members later link TG; email is not unique anywhere (same person = many orders, no join key) — member↔order attribution needs a new nullable `orders.member_id` (additive, safe) rather than email matching.

## 4) Existing reseller-like concepts — mostly misleading

- **TUNVN PREHUB** (docs/agent-rules/tunvn.md): AXVARA is the *downstream reseller* of a Telegram supplier — hidden mirror catalog, AXVARA pays supplier deposits (`callTunvnDeposit`, admin-created invoices, owner transfers manually, tunvn.md deposit section 20 Nov). Reusable: the **supplier-deposit invoice lifecycle** (atomic slot reservation, exact-amount transfer, paid-confirmation polling) as a pattern for *supplier* balances. Misleading for the reseller program: it has no downstream identity, no per-reseller pricing, no customer deposit — nothing faces outward.
- **White-label** (issue/supplier-white-label-2026-11-02.md) is copy/link hygiene (supplier text rewritten to AXVARA branding), **not** a reseller/white-label program. Do not let the name anchor design.
- **Pedia credits** (`pedia_credits`/`pedia_credit_ledger`, schema.sql:1566-1587): buyer-facing store credit from partial/cancelled SMM orders, email-keyed, append-only delta log. Closest existing "balance" but scoped to Pedia refunds; see §6.

## 5) Supplier onboarding cost + adapter contract for multi-step suppliers

A new supplier today touches, at minimum: `src/lib/<s>/{client,sync,orders|purchase,markup,families}.ts` (small suppliers each carry all five; WR/SK add deliver/saldo), mirror tables + `<s>_order_links` + a `fulfillment_items.<s>_link_id` column (schema.sql:613-617 pattern, one migration each), link creation in paid-fulfillment, a cron job name in `LITE_JOBS` (`src/app/api/cron/lite/route.ts:50` — hardcoded list incl. per-supplier `*_orders`/`*_catalog`) **and** a phase block in `src/app/api/cron/operations/route.ts`, admin API routes + `SupplierAdminPanel.tsx` config + a `<S>Manager.tsx`, buyer notifications (per-supplier functions accrete in `src/lib/notify-buyer.ts:254-567`), Telegram catalog/keyboard awareness, env flags + agent-rules doc + ARCHITECTURE section. Refactor #4 (small-supplier claim-CAS helper) reduces the orders.ts duplication only.

**Why virtual numbers don't fit:** the generic fulfillment model is one-shot — `fulfillment_items.status IN ('queued','sending','delivered','manual_required','retry','failed')` (schema.sql:604-605), delivery = one encrypted blob (`delivered_ciphertext`), no buyer-input-after-payment, no supplier-session state, no expiry/cancel-refund window. OTP rental needs: rent → number issued (intermediate deliverable) → wait external event (OTP arrives, buyer may submit/read) → auto-complete at window end or cancel+refund. The only in-repo precedent for multi-step async with cancel/refund is **Pedia** (`pedia_order_items` snapshots, followups, credit-back on cancel) — SMM-shaped, not generic.

**Adapter contract refactor #4 must therefore define** (beyond claim/lease/retry): (a) link lifecycle states incl. `awaiting_event` with a deadline; (b) `onPaid → provision()` returning either credentials, an intermediate artifact (phone number), or pending; (c) `poll(event)` / webhook intake for intermediate events; (d) `cancel()` + `refundPolicy` hook into the order aggregate; (e) intermediate artifact storage (today only terminal ciphertext exists — needs an encrypted intermediate field or link-side payload column). Without (a)-(e) in the contract, a virtual-number supplier becomes a sixth bespoke orders.ts that the next refactor must redo.

## 6) Ledger / balance — nothing customer-facing exists

No wallet, deposit, or commission concept for customers. Append-only-ish logs that exist: `pedia_credit_ledger` (schema.sql:1579-1587: credit_id, order_code, delta, created_at — no balance-after snapshot, no actor, Pedia-scoped, email-keyed credits), supplier-side only: `wr_saldo_log`, `pedia_supplier_balance_log` (schema.sql:1588), SK topup tracking (`src/lib/sekalipay/topup.ts`), TUNVN deposit invoices. Reseller deposits + affiliate commissions need a new double-purpose ledger (owner/member account, signed delta, balance_after, idempotency key, source ref) — model it on `pedia_credit_ledger`'s append-only discipline but as a fresh table; do **not** generalise `pedia_credits` in place (its `source_kind IN ('partial','canceled','admin')` CHECK and email key are Pedia semantics).

## 7) Recommended FOUNDATION refactors (ordered; beyond the 5 hotspots + WR/SK state machine + small-supplier helper)

1. **Extract `placeOrder` domain service from web route + commerce.ts convergence** (§1). Why: reseller API, member checkout and any future channel must share validation/price-bind/anti-abuse/atomic reserve or prices and stock rules will fork. Size **L**, risk **high** (money path; mitigate with characterization tests on web+TG first, keep route as thin adapter). Owner decision: none technical; must not change buyer-visible behaviour.
2. **`resolveSellPrice(variant, qty, tier)` pricing seam** (§2). Why: prerequisite for reseller tier and for API quotes; kills the triple re-validation drift. Size **M**, risk medium. Owner decision: reseller pricing model (%-off retail vs cost-plus) and whether cost may ever be API-visible.
3. **Supplier adapter contract v2 with multi-step lifecycle** (§5), proven by migrating ONE small supplier onto it. Why: must exist before virtual-number supplier is started, else bespoke #6. Size **L**, risk medium-high. Owner decision: refund/cancel policy shape for timed rentals (product decision, affects contract (d)).
4. **Member identity + order attribution**: `members` table, nullable `orders.member_id`, session scheme separate from admin (own secret/cookie scope), optional TG/email linking. Why: reseller dashboard, affiliate attribution and member login all key off it. Size **M**, risk medium (auth — reuse rate-limit/body/audit patterns §3, never admin JWT/Access). Owner decisions: login method (email OTP vs password vs WA), whether guest checkout survives.
5. **Append-only customer ledger + accounts** (§6) with idempotency keys and balance_after. Why: deposits and commissions are both just ledger posters; building either feature first without it creates a second Pedia-credits silo. Size **M**, risk medium-high (money). Owner decisions: deposit rails/top-up methods, commission basis (paid vs delivered), payout policy.
6. **Reseller API key + public API surface** cloned from `agent-auth.ts` shape (own table, scopes like `orders:write`, per-key rate limits via checkout-guard pattern). Blocked by 1+2+4+5 (an API key must resolve to a member/ledger/tier). Size **M**, risk medium. Owner decision: API buyers pay by deposit balance or per-order QRIS — this changes what placeOrder must accept as payment instruction.
7. **Cron job registry** (data-driven job table replacing hardcoded `LITE_JOBS` + operations phases) — only when supplier #6 lands; until then the list is annoying but stable. Size **S-M**, risk low-medium. No owner decision.

**Explicitly do NOT refactor:** buyer PIN/proof/order-access (`order-access.ts`, device cookie) — security-sensitive, owner-approved semantics, zero feature pressure; payment rails (`src/lib/payments/*` invoice issuance per rail) — stable, feature work should call them via placeOrder, not reshape them; TUNVN/Pedia internals — bespoke but working, generalise only via the new adapter for *new* suppliers; catalog copy/white-label pipeline; admin auth/Cloudflare Access — replace nothing, just never reuse it for members.
